# 同步推理与 RTC 推理（第 6500 步中途测试）

实验二训练到第 6500 步时中途停下，做了一次简单的真机测试，并根据测试中的警告和抖动比较了同步推理与 RTC 推理。这里记录测试过程和分析，不作为实验二的结论；实验二的正式结果见[实验二](../experiments/exp2-pilot-v2.md)。

- 训练在第 6720 步停止（2026-10-22 17:56），之后从第 6500 步的存档续训。
- 第 6500 步的 best 复制到 `runs/so101_pilot_v2/snapshot_step6500/best`，权重 sha256 前 16 位 `77c568f9af12faca`。离线验证 0.286，各关节 MAE 5.0/11.8/12.2/6.9/8.5°，夹爪 4.2。已核对其前/后处理器里的归一化统计与训练统计相同。

## "Record loop is running slower (5.4 Hz)" 警告

- 5.4 Hz 相当于一个循环约 185 ms，和一次同步推理差不多（约 165 ms）。
- 每段平均 1106 帧，按 40 s 算平均 27.7 Hz，和实验一（1092 帧，27.3 Hz）相同。
- 30 Hz 本应有 1200 帧。少的约 94 帧，正好是每 50 步一次、每次约 0.18 s 的推理停顿。

所以警告只来自每个动作块开头做推理的那一步，不是整段都慢；两次实验条件相同，结果可以比。代价是机械臂每 1.7 s 停约 0.18 s，动作一走一停，可能加重抖动（未验证）。

## 动作块衔接处的跳变（同步推理）

在三次真机录像里，每 50 步换一个动作块。统计相邻两步动作之间各关节变化的最大值，分别看换块处和块内。

| 录像 | 换块处 中位数 / p90 / 最大 | 块内 中位数 / p90 |
|---|---|---|
| 实验一 钥匙 | 5.0° / 10.3° / 26.5° | 2.3° / 4.5° |
| 实验二 玩偶 | 3.9° / 14.9° / 30.8° | 1.7° / 4.3° |
| 实验二 钥匙 | 3.8° / 8.2° / 25.3° | 1.7° / 3.6° |

也就是每 1.7 s 先停约 0.18 s，然后动作突然跳一下，和用户看到的抖动一致（因果关系未验证）。

## RTC 离线检查

RTC 即 Real-Time Chunking，LeRobot 中用 `--inference.type=rtc` 开启。

用第 6500 步模型，在 6 个验证段里取 24 个时刻做模拟：
1. 在 t 时刻生成动作块 A。
2. 20 步后（队列还剩 30 步），用 t+20 时刻的画面生成新块，假设推理延迟 6 步。
3. 比较新块第一个被执行的动作和 A 最后执行的动作，取各关节差值的最大值。

| 新块 | 衔接跳变 中位数 / p90 / 最大 | 推理耗时 中位数 / 最大 |
|---|---|---|
| 普通（不引导） | 13.4° / 23.4° / 36.4° | 186 / 197 ms |
| RTC（execution_horizon 10，max_guidance_weight 10） | 1.6° / 4.1° / 6.5° | 232 / 276 ms |

- A 自己相邻两步之间变化的中位数是 1.65°，所以用 RTC 后，衔接处的跳变和块内一步差不多。显存 1.83 GB。
- 离线时 t+20 的画面来自人类示教，而不是 A 执行后的真实状态，所以普通新块的跳变会偏大。真机上同步推理的衔接跳变见上一节。

## RTC 执行视野改为 20

第一次真机 RTC 运行时出现警告：`Indexes diff is not equal to real delay. indexes_diff=10, real_delay=11`。

- 意思是一次推理实际花了约 11 步的时间（超过 0.33 s，比离线测的 232 ms 慢，可能是相机、显示和推理线程同时占资源）。
- LeRobot 按 11 步丢掉新块开头，比实际执行掉的多丢 1 步。
- LeRobot 的引导权重规则：新块前 `delay` 步固定沿用旧块，之后线性递减，到 `execution_horizon` 处降为 0。
- 所以延迟 11 步、而视野只有 10 时，真正被执行的那些动作完全没有受到引导。

用同样的 24 个时刻、假设延迟 11 步，离线比较：

| 新块 | 第一步跳变 中位数 / p90 / 最大 | 之后 10 步偏离旧块 中位数 |
|---|---|---|
| 普通 | 15.9° / 27.7° / 37.0° | 24.9° |
| RTC 视野 10 | 5.4° / 7.5° / 9.1° | 12.8° |
| RTC 视野 20 | 2.8° / 6.4° / 8.3° | 6.3° |

`scripts/eval.fish --rtc` 改用视野 20。`queue_threshold` 为 30 时，旧块还剩 30 步，够用。已用假串口确认 `lerobot-rollout` 接受这些参数，并能加载开启了 RTC 的策略。

## 真机 RTC（视野 10，玩偶，2026-10-22 18:30 左右）

评测名 `rollout_pilot_v2_s6500_doll_rtc`，模型同样是第 6500 步。

| 推理 | 成功 | 平均控制频率 | 相邻步动作变化 中位数 / p90 / p99 / 最大 |
|---|---|---|---|
| 同步 | 3/10 | 27.7 Hz | 1.72° / 4.46° / 9.81° / 30.8° |

- 场景右侧多了一本白色笔记本，训练数据里没有，外观接近白盒，可能造成干扰（未验证）。

## RTC 重置后用旧观测推理（2026-10-23 发现并修复）

纠错采集时发现，交还模型的那一刻，机械臂有时会突然往**接管前**的方向猛动（24 次交还里最大的三次单步跳变分别为 83.5°、58.6°、39.9°，模型的第一个动作都更接近接管前的指令，而不是人松手时的位置）。

原因在 LeRobot 的 `RTCInferenceEngine.reset`：它只清空动作队列，不清除后台线程保存的"最新观测"。

- 恢复推理后，主循环要先读一次相机才能送入新观测。后台线程如果在这几十毫秒内先醒来，就会用旧观测推理出一整块动作。
- 如果重置的那一刻正好有一次推理在进行，它算完的结果会在队列清空之后才被放进去。

这样，一段新尝试的开头可能执行的是用上一段最后一帧规划的动作块，交还模型时则可能执行接管前规划的动作块，持续约 0.7 s，直到下一块出来。同步推理每次都用当前观测现算，不受影响。

已有录像中的情况：比较每段前 10 帧的指令与起始状态，同步推理（`rollout_pilot_v2_s6500_doll`）最大 7.8°；RTC 录像中出现了 143°（`rollout_pilot_v2_final_key_rtc_s2` 第 4 段：`shoulder_lift` 起始在休息位 -102.9°，前 0.7 s 的指令却在 38–41°，与第 3 段结尾的 34–44° 一致，可以确认是用上一段末帧推理的），以及 28.7°、22.5°、14.1°（这三段的指令看起来像正常的起步运动，不能确认）。因此实验二 RTC 评测中至少有一段开头执行了用旧观测规划的动作；这对成功率的影响未测量。

修复（`so101vla/rollout.py`，`eval.fish`、`try.fish`、`dagger.fish` 都会经过这里，始终生效）：重置时同时清除保存的观测，后台线程会等到新观测送来才推理；并换用一个新的动作队列，正在进行的旧推理算完后，结果会放进已经弃用的旧队列。验证（`scripts/rtc_selftest.py`）：运行真实的 RTC 后台线程，模型用桩替代（返回的动作块用观测值填充，可以看出它是根据哪一帧算的）。"交还时线程抢先"和"重置时推理正在进行"两种情况下，原版的重置后第一个动作都来自旧观测，修复后都来自新观测，连续跑 3 次结果相同。修复后还没有在真机上重新测试。

## RTC 在新动作块开头跳过十几步（2026-10-24 发现并修复）

在旧观测问题修复之后录的纠错数据里（玩偶第 10–29 段、钥匙第 0–29 段），交还模型时仍有 15–31° 的单步跳变（玩偶最大 29.8°，钥匙最大 30.6°）。检查结果：

- **不是主臂同步的问题**：交还时刻，主臂最后的位置和从臂实测位置相差中位数 1.4°（玩偶）/ 2.3°（钥匙），最大 3.4° / 5.0°；而模型第一个动作和从臂实测位置最多相差 30.0° / 30.8°。接管时刻，从模型最后一帧到主臂第一帧，从臂实测只移动了中位数 1.0–1.5°，最大约 7°。
- **也不是旧观测**：跳变之后，模型的动作沿跳变方向平稳地继续（每帧 1.5–2.5°），没有往接管前的姿态拉回；跳变幅度约等于"每帧速度 × 11 帧左右"。

原因：LeRobot 的 `ActionQueue.merge` 在 RTC 模式下替换队列时，按推理耗时估算出的步数（`ceil(耗时 / 帧间隔)`，约 11 步）丢掉新动作块的开头，认为这些步在推理期间已经执行过了。但在一段刚开始时，以及纠正后刚交还时，队列是空的，机械臂一直停着没动，实际执行了 0 步。丢掉这 11 步后，机械臂会直接跳到模型计划中约 0.37 s 之后的位置。LeRobot 自己也计算了实际执行的步数（`indexes_diff`），两者不一致时只打印 `Indexes diff is not equal to real delay` 警告，仍按估算值丢弃。

修复（`so101vla/rollout.py`，与旧观测修复一起始终生效）：按推理期间实际执行的动作数丢弃。正常运行时，两者一般只差 0–1 步，行为基本不变。验证（`scripts/rtc_selftest.py`，桩模型的第 k 步返回"观测值 + 0.01k"，因此能看出从第几步开始执行）：原版在重置后从第 1 步或第 10 步开始执行，并且不论推理期间执行了 0 步还是 3 步，都固定丢掉 11 步；修复后从第 0 步开始，执行了 0 步就丢 0 步，执行了 3 步就丢 3 步，连续跑 3 次结果相同。修复后还没有在真机上重新测试。
