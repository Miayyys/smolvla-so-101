# 端侧支线：v5 部署到 RK3588（2026-11-05 至 11-07；一次推理 6.11 s → 4.06 s 无损，专家 INT8 3.45 s）

**定位**：2026-11-07 起端侧部署改为支线，主线转向 real2sim2real（见 [plan.md](../plan.md)）。本文记录到停下时为止的全部结果和踩过的坑，以后回到端侧可以从这里接着做。

**对象**：实验四第二阶段的浮点基线 `runs/so101_full_v5/best`（两路相机，512 分辨率，10 步去噪，每块 50 步动作）。

**结论**：

| 配置（8 个测试帧，每帧一次完整推理） | 视觉 ×2 | prefix | 专家 ×10 | **合计** | 峰值内存 | 动作误差（关节平均 / 最大） |
|---|---:|---:|---:|---:|---:|---|
| LeRobot 原样导出，FP16 | 2652 ms | 601 ms | 2878 ms | 6.11 s | 1.57 GB | 0.17° / 1.2° |
| 改写图 + 裁掉语言补齐位，FP16 | 2682 | 464 | 2475 | 5.62 s | 1.46 GB | 0.15° / 1.3° |
| **+ K/V 每块只上传一次 + 两路视觉分核并行** | 2038 | 470 | 1527 | **4.06 s** | 2.02 GB | 0.15° / 1.3°（不变） |
| 再把专家换成 INT8 | 2041 | 464 | 936 | 3.45 s | 1.81 GB | 0.95° / 7.5° |
| 再把视觉换成 INT8 | 1360 | 463 | 968 | 2.82 s | 1.45 GB | 1.68° / 28° |

- 不损失精度的优化把一次推理从 6.11 s 降到 4.06 s（−34%）。按现在的 RTC 设置（队列剩 30 步时重新规划），推理需要在约 1 s 内完成，差 4 倍；按每块执行完 50 步再推理的预算（1.67 s），差 2.4 倍。
- 视觉占一半时间，且主要是 1024 个 token 的注意力本身，没有无损的手段了。剩下的办法（降分辨率、减少去噪步数、减少专家层数、视觉 INT8 混合精度）都会改变模型输出，需要重新训练或真机闭环验证。停在这里是因为板子算力有限，继续投入的收益不大。
- 动作误差都是相对 LeRobot 在 PC 上 FP32 推理的输出（同一帧、同一噪声），不是成功率。没有做过闭环测试。

第一行来自 LeRobot 原样导出的图（48 个语言位），原始报告在重新导出时被删了（见文末"文件"）；其余四行的原始报告在 `runs/rknn_v5/board/`。第一行和后几行的测试帧不完全相同，比较时只看大致幅度。

## 一、环境

- **板子**：LZAMP RK3588S，Ubuntu 22.04，3.8 GB 内存、无 swap，7 个核在线（0–2 是 A55，3–6 是 A76），NPU 驱动 0.9.8，`librknnrt` 2.3.2，不能上网，见 [hardware.md](../hardware.md)。根分区原来是满的，11-06 清理（删掉 QVLA 时期的 LIBERO 产物，日志压到 100 MB）；工作目录放在 `/userdata/so101`，板端 Python 环境在 `/userdata/so101/board_env/python_site`（rknn-toolkit-lite2 2.3.2、numpy 1.26.4 等）。
- **PC**：RKNN-Toolkit2 2.3.2 装在单独的 `.venv-rknn`（Python 3.12、torch 2.4.0 CPU 版），因为它要求 `torch<=2.4.0`、`numpy<=1.26.4`，和主环境冲突。onnx 必须降到 1.16.1：Toolkit2 2.3.2 用到的 `onnx.mapping` 在新版 onnx 里已经删掉。主环境加了 onnx（`torch.onnx.export` 需要）。命令见 [commands.md](../commands.md) 第 11 节。

## 二、导出：三张子图（`so101vla/rknn_export.py`）

| 子图 | 输入 → 输出 | 每次推理调用 |
|---|---|---|
| 视觉 | 像素 `[1,3,512,512]` → 64 个图像 token（连接层输出 × √960） | 2 次（每路相机一次） |
| prefix | prefix 嵌入 `[1,P,960]`、注意力屏蔽、RoPE 的 cos/sin → 16 层 K/V | 1 次 |
| 专家 | `x_t`、时间嵌入、prefix 屏蔽、RoPE、16 层 K/V → 速度 `[1,50,32]` | 10 次 |

留在 CPU 上的部分：图像缩放和归一化、分词和词嵌入、状态归一化和 `state_proj`、时间嵌入、Euler 循环、动作反归一化。测速时这些都没有计时（图像缩放等以后需要单独测）。

- **参考值**：用 LeRobot 自己的 `predict_action_chunk` 在 CPU 上以 FP32 运行，用 hook 记下每个模块边界的输入输出。每张图导出前都和参考值逐元素核对（相对误差 < 1e-5），onnxruntime 上再核对一次（约 1e-7）。
- **数据**：从 v5 自己的真机录像（`rollout_full_v5_doll_raised`、`rollout_full_v5_key_raised`）里抽帧：24 帧做校准，8 帧做测试。测试帧来自每个数据集最后 4 段，和校准帧不重叠。专家的 40 个校准样本在 10 个去噪步上均匀分布。
- **导出时的改写**（都已验证和 LeRobot 一致）：
  - RoPE 不用切片赋值（会变成 ScatterND）；
  - 注意力屏蔽值用 -1e4，不用 float32 最小值（FP16 下会变成 -inf，整行被屏蔽的补齐 token 会算出 NaN）；
  - 浮点 0/1 屏蔽用 `Cast` 转成布尔，不用 `> 0.5`（见三.3）；
  - 默认使用 `--graph fast` 改写图（见五）和 `--lang-slots 16`（见五.2）。

## 三、板上遇到的问题

### 1. prefix 和专家在 NPU 三核模式下结果是错的

同一个 prefix FP16 模型，KV 和参考值的相对误差：

| 核心 | 延迟 | 第 0 层 | 第 7 层 | 第 15 层 |
|---|---:|---:|---:|---:|
| 单核 `core0` | 759 ms | 0.29% | 0.31% | 0.25% |
| 三核 `core012` | 688 ms | 0.29% | 8.6% | 24% |

专家 INT8 在三核下也一样：反而更慢（228 ms 对比单核 197 ms），余弦只有 0.84，只看专家的动作误差约 19°。视觉在三核下是正确的，误差和单核相同，而且快 30%（1336 ms 对比 1939 ms）。所以 prefix 和专家只能单核运行。测速脚本的默认设置：视觉三核，prefix 和专家单核。

误差最大的是状态 token 和语言的前几个 token，随层数逐层累积。RKNN 模拟器（`accuracy_analysis`）复现不出这个问题：模拟器里的 FP16 prefix 最后几层余弦 0.99999–1.0。

### 2. "FP16 下 RMSNorm 溢出"这个推测是错的

导出时发现，腕部相机有几个图像 token 在通道 87、439、40 上约为 14,000（连接层输出约 450，乘 √960 后到这个量级），16 层里一直保持。视觉 `post_layernorm` 的输入最大约 955。它们的平方都超过 FP16 的上限 65504。

我推测 prefix 的误差来自 Norm 溢出，于是把 Norm 改成"先除以每个 token 的最大绝对值再算"（数学上等价）。结果误差没变（27%），三张图反而都变慢了：视觉 1334 → 1948 ms，prefix 429 → 645 ms，专家每步 290 → 331 ms。真正的原因是三核（三.1）。这个改写保留成默认关闭的选项 `--scale-norms`。

### 3. INT8：屏蔽里的比较算子在板上失败，rknnlite 不报错

第一次测 INT8 时，prefix 的余弦是 −0.06，专家是 0.02，看起来却快得惊人（prefix 20 ms，专家每步 49 ms）。用 C 接口运行时，板端打出了：

```
ElementwiseLogical: unsupported A type: INT8, B type: FLOAT!
Op type:Greater ... fallback cpu failed
```

图里的 `mask > 0.5` 在 INT8 模型中，是"量化成 INT8 的输入和浮点常数比较"，这个算子要退回 CPU，但 CPU 实现不支持这种组合，直接失败。屏蔽变成了垃圾值，大量计算根本没有执行，所以才"快"。rknnlite 不报错，模拟器里正常（专家 INT8 余弦 0.9956）。

改用 `mask.to(bool)`（Cast）和 `mask > mask*0.5` 都能修好，两者在 FP16 和 INT8 下结果完全一致，默认用 Cast。修好后专家 INT8 每步 228 ms，余弦 0.9967，**只比 FP16（303 ms）快 1.3 倍**。

还试过一个办法：先算 softmax，再乘 0/1 屏蔽并重新归一化（为避免精度损失，最大值只在有效位置里取）。这个写法在 FP32 下等价，但每个注意力要多出约 10 个算子，板上 FP16 都算错了（专家余弦 0.87），而且慢了一倍，已放弃。

### 4. prefix INT8 的损失是真实的

模拟器的 INT8 逐层分析和板上一致：prefix 的 K 余弦从第 0 层的 0.93 降到第 15 层的 0.90。单层误差最大的是 RMSNorm（单层余弦 0.82–0.96）和 RoPE 的 Sin（0.98）。原因：
- prefix 输入按整个张量共用一个缩放系数，被 ±14,000 撑开后每档约 110，语言 token 和状态 token（几到几十）几乎都被量化成 0；
- 位置编号（0–176）被量化成 INT8，每档约 0.7。

改写图（五）把 RoPE 改成在 CPU 上算好 cos/sin 再输入，解决了后一个问题，但 prefix INT8 的余弦仍是 0.89。没有继续处理，候选办法是混合精度（残差流和 Norm 保留 FP16）或 SmoothQuant，见 [quantization-methods.md](../quantization-methods.md)。

### 5. 两个接口上的细节

- rknnlite 的 4 维输入默认按 NHWC 解释，要传 `data_format='nchw'`。KV `[1,5,P,64]` 如果按 NHWC 传，FP16 专家的余弦会降到 0.81。
- C 接口的浮点 4 维输入只接受 NHWC，NCHW 会报 `unsupported src layout for normalize`。

## 四、时间花在哪里（逐算子性能分析，`scripts/board_profile.py`）

这些数据来自 `RKNN_QUERY_PERF_DETAIL`，是 NPU 和 CPU 上各算子的时间之和，不含 Python 和输入转换的开销。

| 子图（LeRobot 原样导出，修好屏蔽后） | 总计 | 主要部分 |
|---|---:|---|
| 视觉 FP16，三核，每路相机 | 1267 ms | 注意力 `exSDPAttention` 714 ms（56%）；矩阵乘约 480 ms；Norm 63 ms |
| 视觉 INT8，三核，每路相机 | 1571 ms | 注意力 1171 ms（**比 FP16 慢**）；矩阵乘约 270 ms |
| prefix FP16，单核 | 570 ms | 矩阵乘约 270 ms（47%）；Transpose 98 ms；softmax 95 ms；CPU 上的 Sin/Cos 23 ms |
| 专家 INT8，单核，每步 | 206 ms | Transpose 64 ms（82 次，31%）；softmax 37 ms（18%）；矩阵乘约 49 ms（24%）；其他逐元素运算约 50 ms |

专家每步只有四分之一的时间在做矩阵乘，所以 INT8 只能快 1.3 倍。这是改写计算图的出发点。

## 五、无损优化

### 1. 改写 prefix 和专家的计算图（`so101vla/rknn_fast.py`）

直接用 checkpoint 的权重手写前向，不再调用 LeRobot 的模块；导出前逐元素核对，误差 ≤ 1e-6。

- **第一次改写（失败）**：把共用同一 K/V 头的 3 个查询头叠到序列方向，注意力分数变成 `[1,5,3T,S]`。RKNN 对这个形状的 softmax 退回 CPU 执行：专家 INT8 的 softmax 从 NPU 上的 37 ms 变成 CPU 上的 139 ms，prefix FP16 退化到 1.2 s。RoPE 改用 64×64 矩阵乘，又增加了转置（82 → 154 次）。结论：**RKNN 对形状很敏感，LeRobot 原来的 `[1,15,T,S]` 正是它擅长的形状，每次改动都要上板实测。**
- **第二次改写（保留）**：
  - 注意力保持 `[1,15,T,S]` 的形状；
  - K/V 按头优先 `[1,5,P,64]` 传入和输出，省掉缓存的来回转置；
  - 专家交叉注意力层（奇数层）对 prefix K/V 的投影挪进 prefix 图，每块只算一次；
  - RoPE 改用 CPU 算好的 cos/sin 作为输入，用 split/concat 旋转；
  - 1/8 缩放并进 q；
  - prefix 最后一层只算 K/V，后面的注意力和 MLP 不再计算。

  图的节点数：专家 2432 → 1003，prefix 2417 → 1124。

  交叉注意力投影本身很小，每步约 2 ms，主要收益来自去掉的转置和 CPU 上的 Sin/Cos。

### 2. 裁掉语言补齐位（`--lang-slots`）

分词器把指令补齐到 48 个 token，而两条任务指令都只有 9 个有效 token。保留 16 个语言位后，prefix 从 177 个 token 缩短到 145 个。补齐位在所有地方都被屏蔽，所以结果不变，专家输出和 LeRobot 逐元素核对过。如果指令超过 16 个 token，导出会直接报错。

### 3. 三组对照（2 个测试帧，单位 ms）

基线是 LeRobot 原样导出、48 个语言位：prefix FP16 585 / INT8 522，专家每步 FP16 303 / INT8 228。

| 变体 | prefix FP16 | prefix INT8 | 专家 FP16 | 专家 INT8 | 只看专家的动作误差（INT8） |
|---|---:|---:|---:|---:|---|
| A 只裁剪 | 494 | 422 | 281 | 226 | 1.07–1.58° |
| B 只改写 | 578 | 546 | 273 | 198 | 0.91–0.99° |
| C 改写 + 裁剪 | 484 | 446 | 245 | 207 | 0.93–1.00° |

C 的专家 INT8 每步 NPU 时间降到 180 ms，其中 Transpose 52 ms（76 次）、softmax 32 ms，剩下的大多是多头注意力在这块 NPU 上的固有开销。

### 4. K/V 每块只上传一次（`scripts/rknn_capi.py`，`board_bench.py --kv-resident`）

运行时会保留上一次设置的输入。每块开始时设置一次全部输入，之后每步只重新设置 `x_t` 和时间嵌入，输出和每步全部重新设置时逐元素相同（最大差 0）。原来每一步都要在 CPU 上把 32 个 K/V 张量从 float32 转成原生格式（INT8 量化或转成 FP16，再转成 `NC1HWC2` 布局，通道从 5 补齐到 16 或 8）。

| 专家 10 步（C 接口，测试帧 0） | 每步全部重新设置 | 每块只设置一次 |
|---|---:|---:|
| FP16 | 2370 ms | 1602 ms（−32%） |
| INT8 | 1803 ms | 1000 ms（−45%） |

rknnlite 不提供这个能力，所以用 ctypes 直接调 C 接口。

### 5. 两路视觉分核并行（`board_bench.py --vision-parallel`）

两路相机分别在核 0 和核 1 上用两个线程并行跑：2038 ms；原来两路都用三核、一路接一路地跑：2716 ms。结果相同。代价是视觉模型要加载两份，内存多约 0.45 GB。视觉 INT8 在单核下比三核下好得多：两路并行 1360 ms，而原来三核顺序是 2264 ms。

## 六、RTC 在板上能不能用

LeRobot 0.6.1 的 RTC 实现（`policies/rtc/modeling_rtc.py`）里虽然调用了 `torch.autograd.grad`，但 `v_t` 是在打开 `x_t` 的梯度之前算出来的，所以求导结果是单位矩阵，修正项就是误差本身，**并没有对专家做反向传播**。用一个非线性玩具去噪函数验证过：修正项和误差的最大差为 0，而论文的向量-雅可比积与它相差 14。所以 RTC 在板上只需要前向推理加几个逐元素运算，能用。限制在于延迟：现在的设置是剩 30 步时重新规划、引导范围 20 步，推理需要在约 1 s 内完成，最好在 0.67 s 以内。

## 七、没有做的事

- 视觉 INT8 的精度（混合精度，让注意力保留 FP16）；
- prefix INT8 的精度（混合精度或 SmoothQuant）；
- 板端 CPU 部分（图像缩放、分词、词嵌入）的耗时；
- 整条链的端到端部署：相机和机械臂接到板上，或者电脑采集后把数据发给板子；
- 闭环成功率；
- 会改变输出的加速办法：去噪步数、图像分辨率、专家层数。
